# omacharts — spec

**Status:** draft, v0 scope
**Last updated:** 2026-10-03

A GTK app for watching world markets — indexes, futures, equities, FX and
crypto — with fast, good-looking charts.

See [analysis.md](analysis.md) for the market-data research this builds on.

## Who it is for

People who **traverse a lot of charts quickly at a high level** — swing
traders, investors, anyone keeping an eye on markets. The core loop is flipping
through dozens of symbols looking at daily and weekly structure, dropping to
intraday when something is interesting, and moving on.

That loop is the whole design brief. Every chart opened is a chart someone is
about to leave, so opening one must cost nothing.

**TradingView is the role model** for how that should feel: type a few
characters and the instrument is there, charts that pan and zoom without
thinking, timeframes a keystroke away.

**No trading logic inside.** No orders, no broker connection, no positions, no
P&L, no backtesting, no strategy evaluation. It shows markets; it does not
reason about them or act in them. Intraday data is there to look at, not to
trade from.

**It must feel native on Linux.** libadwaita and GNOME HIG, system theme,
standard shortcuts and window behavior. TradingView's speed, not its chrome.

## Driving principle: speed

Speed is the product. Traversing charts only works if traversal is free, so
every design decision below resolves in its favor.

| Interaction | Budget |
|---|---|
| Keystroke → search results | **< 1 ms** |
| Open a cached chart → first paint | **< 16 ms** (one frame) |
| Pan / zoom | **60 fps**, no allocation in the draw path |
| Launch → interactive window | **< 200 ms** |
| Network on any paint path | **never** |

The rules that follow from this:

- **Nothing already downloaded is ever downloaded again.**
- **The network is never on the critical path.** Cached data paints first,
  fresh data arrives and repaints.
- **SQLite is never queried on the typing path.**
- **No work on the UI thread** beyond drawing.

## Non-goals

- Orders, broker connectivity, positions, P&L, backtesting — no trading logic
- Real-time data (v0 is delayed; see the Yahoo adapter)
- Individual futures contract months, term structure, spreads
- Options, mutual funds, warrants
- Any hosted component

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Stack | **Rust + GTK4 + libadwaita** | Same as omatm |
| Instrument identity | **Synthetic ID + mappings** | No adapter is privileged; Yahoo's quirks stay out of the schema |
| Futures granularity | **Continuous roots only** | Yahoo only serves `=F`; contract months are not needed to watch a market |
| Inventory scope | **Global** | US + world indexes + CME futures + FX + crypto + major foreign exchanges |
| Symbol inventory | **Shipped in repo**, refreshed daily in background | Works offline on install, stays current without blocking |
| Market data | **Cached locally in SQLite**, never in the repo | Download once, keep forever |
| v0 adapter | **Yahoo only** | Keyless and covers every instrument type |

## Architecture

Mirrors omatm: a GTK-free engine crate linked by the app, with the app holding
everything that touches GTK.

```
omacharts/
  Cargo.toml                 workspace
  crates/omacharts-engine/   no GTK, no rusqlite
    symbols/                 in-memory index, search, ranking
    mapping/                 adapter symbol templates
    bars/                    aggregation, session-aware resampling
    adapters/yahoo/          HTTP, parsing, cache policy
  src/                       the app
    main.rs
    store.rs                 rusqlite — the local database
    refresh.rs               background symbol-inventory refresh
    settings.rs
    ui/
  data/symbols.db            shipped seed, generated by CI
  tools/build_symbols.py     generator
```

Dependencies follow omatm: `gtk4`, `libadwaita`, `rusqlite` (bundled),
`async-channel`, `chrono` + `chrono-tz`, `serde`. Edition 2024.

**The engine never links rusqlite or GTK.** SQLite is a storage format owned by
the app; the engine receives plain structs. Cheap to compile, testable without
a database.

## Storage — two databases

### 1. `data/symbols.db` — shipped seed, in the repo

Read-only instrument inventory, generated by CI. Ships with the app so search
works offline the moment it is installed. Never written to at runtime.

### 2. `$XDG_DATA_HOME/omacharts/omacharts.db` — local, never in the repo

Everything mutable, following omatm's single-database convention
(`~/.local/share/omacharts/omacharts.db`, WAL mode):

- **Cached market data** — the bars, downloaded once
- **Settings** — key/value, serde-serialized
- **Refreshed symbol inventory** — supersedes the shipped seed when present

This file is pure app data. It is in `.gitignore`, never committed, and safe to
delete — the app rebuilds it from the seed and refetches on demand.

## Data model — symbols

The canonical instrument is a neutral row; every adapter symbol — including
Yahoo's — lives in `symbol_mappings`.

```sql
CREATE TABLE markets (
  id            INTEGER PRIMARY KEY,
  mic           TEXT UNIQUE,        -- XNAS, XLON, XETR, XCME…
  name          TEXT NOT NULL,
  country       TEXT,               -- ISO 3166-1 alpha-2
  timezone      TEXT NOT NULL,      -- IANA, e.g. 'America/New_York'
  session_type  TEXT NOT NULL,      -- 'equity' | 'futures_23h'
  session_open  TEXT,
  session_close TEXT
);

CREATE TABLE instruments (
  id               INTEGER PRIMARY KEY,
  canonical_symbol TEXT NOT NULL,   -- 'AAPL', 'ES', 'GSPC' — neutral
  name             TEXT NOT NULL,
  type             TEXT NOT NULL,   -- equity|etf|index|future_root|fx|crypto
  market_id        INTEGER REFERENCES markets(id),
  currency         TEXT,
  tier             INTEGER NOT NULL DEFAULT 2,  -- 0..3, drives ranking
  UNIQUE (canonical_symbol, market_id)
);

CREATE TABLE symbol_mappings (
  instrument_id  INTEGER NOT NULL REFERENCES instruments(id),
  adapter        TEXT NOT NULL,     -- 'yahoo' (v0)
  adapter_symbol TEXT NOT NULL,
  PRIMARY KEY (adapter, adapter_symbol)
);
CREATE INDEX idx_mappings_instrument ON symbol_mappings(instrument_id, adapter);

CREATE TABLE future_roots (
  instrument_id   INTEGER PRIMARY KEY REFERENCES instruments(id),
  exchange        TEXT NOT NULL,    -- CME|CBOT|NYMEX|COMEX
  tick_size       REAL,
  multiplier      REAL,
  contract_months TEXT,             -- 'HMUZ'
  session_open    TEXT NOT NULL     -- '18:00' ET — drives session resampling
);
```

### Why `future_roots.session_open` matters

Futures sessions open at 18:00 ET. Naive resampling buckets on midnight,
producing 4H bars that silently disagree with every other tool. The session
origin lives in the schema so resampling is correct by construction.

## Data model — cached market data

Columnar, following omatm's `minute_cache`: arrays of bars stored as BLOBs per
chunk rather than a row per bar. Orders of magnitude fewer rows, one decode per
read, and it loads straight into the draw path.

```sql
CREATE TABLE bar_cache (
  instrument_id INTEGER NOT NULL,
  interval      TEXT NOT NULL,      -- '5m'|'15m'|'1h'|'1d'
  chunk_start   INTEGER NOT NULL,   -- unix ts of first bar in chunk
  count         INTEGER NOT NULL,
  ts            BLOB NOT NULL,      -- packed i64
  open          BLOB NOT NULL,      -- packed f64
  high          BLOB NOT NULL,
  low           BLOB NOT NULL,
  close         BLOB NOT NULL,
  volume        BLOB NOT NULL,
  PRIMARY KEY (instrument_id, interval, chunk_start)
);

CREATE TABLE bar_coverage (
  instrument_id INTEGER NOT NULL,
  interval      TEXT NOT NULL,
  first_ts      INTEGER NOT NULL,
  last_ts       INTEGER NOT NULL,
  last_fetch_at INTEGER NOT NULL,
  PRIMARY KEY (instrument_id, interval)
);

CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
CREATE TABLE meta     (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

### Fetch policy — download once, never again

`bar_coverage` answers "what do we already have" without touching `bar_cache`.

1. **Paint from cache first.** Open a chart, read the chunks, draw. No network
   involved, no waiting.
2. **Fetch only the tail.** If `last_ts` is older than one bar period, request
   from `last_ts` forward — never a range already covered.
3. **Completed bars are immutable.** They are written once and never refetched.
4. **The last cached bar is always provisional.** It may have been forming when
   stored, so it is refetched and overwritten on every tail fetch.
5. **Backfill extends, never duplicates.** Asking for more history fetches only
   what precedes `first_ts`.

### Split and dividend invalidation

Yahoo returns adjusted prices, so a split rewrites an equity's entire history
retroactively — cached bars silently stop matching.

Cheap guard: every tail fetch overlaps the last few cached bars. If the overlap
does not match, the instrument's cache for that interval is dropped and
refetched. Costs a handful of comparisons per fetch and catches the case
exactly when it happens.

### Clearing the cache

Settings carries **Clear cached market data**, showing the space in use. It
truncates `bar_cache` and `bar_coverage` and runs `VACUUM`. Settings and the
symbol inventory are untouched. The app keeps working — it just refetches.

## Search — instant by construction

**SQLite is never queried on the typing path.** At startup the app reads the
instrument table once and hands the engine a compact in-memory index; every
keystroke searches that.

- ~13k rows today, ~150k with full global equity coverage — tens of MB of RAM
  at the high end, trivial for a desktop app
- Interned strings, lowercased once at load, prefix buckets by first 1–2 chars
- A query scans a few hundred candidates, not 150k
- **Budget: < 1 ms.** The keystroke and the result land in the same frame

Loading happens off the UI thread (omatm's `std::thread::spawn` +
`async_channel::Sender` pattern). Until it lands, a curated tier-0 set is
searchable, so the window is useful immediately.

### Ranking

Scoring, highest first:

1. Exact `canonical_symbol` match
2. `canonical_symbol` prefix
3. Name prefix
4. Name substring

Each multiplied by a **tier weight**:

| Tier | Contents |
|---|---|
| 0 | Curated majors — world indexes, front-month futures, top ETFs, mega-caps |
| 1 | S&P 500 constituents, major foreign blue chips |
| 2 | Everything else listed |
| 3 | Excluded entirely — test issues (flagged in the Nasdaq file), delisted |

Without tiers, typing `GC` surfaces a microcap above gold futures and the thing
feels broken. With tiers it feels psychic. **This is the most important detail
in the search implementation** — the index is the easy half.

## Symbol mapping

Do **not** store a mapping row per instrument per adapter. Store a **template
per (adapter, instrument type)**, plus an exceptions table for the rest.

| Adapter | equity / etf | index | future_root | fx | crypto |
|---|---|---|---|---|---|
| yahoo | `{ticker}` + suffix, `.`→`-` | `^{code}` | `{root}=F` | `{base}{quote}=X` | `{base}-{quote}` |

Yahoo exchange suffixes: US none, London `.L`, XETRA `.DE`, Paris `.PA`,
Tokyo `.T`, Toronto `.TO`, Madrid `.MC`, Milan `.MI`, Amsterdam `.AS`,
Swiss `.SW`, Stockholm `.ST`, Oslo `.OL`, Sydney `.AX`, Hong Kong `.HK`.

Known transforms: class shares use `-` (`BRK.B` → `BRK-B`). Exceptions that
follow no rule go in `symbol_mappings` explicitly.

A dozen rules cover the whole inventory. Adding an adapter later means adding a
column to this table, not regenerating anything.

## Symbol inventory refresh

The shipped `data/symbols.db` is the floor. A refreshed copy lives in the local
database and takes precedence when present.

**On launch the app spawns a background refresh.** It never blocks startup,
never blocks search, never touches the UI thread beyond posting completion.

- **At most once per day.** `meta.symbols_generated_at` is the gate; under 24h
  old and it exits without a single request.
- Fetches the sources, rebuilds into a temp table, swaps atomically. A failed
  or partial refresh leaves the working inventory untouched.
- A refresh landing mid-session does not disturb the live in-memory index — it
  is picked up on next launch.
- Failures are silent beyond a timestamp in settings. A stale symbol list is
  not worth interrupting anyone over.

### Settings

- **Refresh symbols automatically** — on by default, the once-per-day behavior
- **Refresh now** — manual, ignores the 24h gate
- **Last refreshed** — timestamp and resulting row count
- **Clear cached market data** — see above

## Generator and sources

`tools/build_symbols.py` assembles the inventory from a **registry of
per-source fetchers**, so adding an exchange is adding one fetcher. The same
generator runs in CI and in the on-device refresh.

### Verified working (2026-10-03)

| Source | Rows | Gives |
|---|---|---|
| `nasdaqtrader.com/dynamic/SymDir/nasdaqtraded.txt` | 13,297 | All US equities + ETFs, name, listing exchange, ETF flag, test-issue flag |
| `sec.gov/files/company_tickers.json` | 10,440 | ticker → CIK → legal name, for cross-check |

### Curated, hand-maintained

- **World indexes** (~50) — no public registry exists
- **CME futures roots** (~60) — tick size, multiplier, contract months, session open
- **FX pairs** (~30) and **crypto** (~30) — deterministic symbology

### Global equities — staged by source availability

No single free authoritative directory covers foreign exchanges; each venue
publishes its own file in its own format. Each is a separate fetcher, enabled
as implemented:

| Exchange | Source | Status |
|---|---|---|
| LSE | London Stock Exchange instrument list | planned |
| XETRA | Deutsche Börse listed instruments | planned |
| Euronext | Euronext listed companies | planned |
| TSX | TMX listed issuers | planned |
| JPX | JPX listed companies | planned |
| BME | BME listed companies | planned |

v0 ships US + curated world indexes/futures/FX/crypto. Global coverage lands
exchange by exchange with no schema change — each fetcher emits the same
`(market, canonical_symbol, name, type)` tuples.

### Validation

Validate **only the curated tiers** against Yahoo at build time, heavily
throttled. The 13k US equities follow a deterministic rule; the ~170
hand-written index, futures and FX symbols are where typos live.

### CI

Weekly job rebuilds `data/symbols.db`, commits if changed. Deterministic output
so diffs are reviewable. Target ~3–5 MB.

## Yahoo adapter (v0)

**Endpoint:** `https://query1.finance.yahoo.com/v8/finance/chart/{symbol}`

Use `v8/finance/chart` for everything, quotes included —
`meta.regularMarketPrice` carries the quote. The older `v7/finance/quote` needs
a cookie + crumb handshake; the chart endpoint needs none. This is why the
Omarchy plugin ecosystem consolidated on it.

### Intervals

| Interval | History available | Use |
|---|---|---|
| `1d` | decades | daily and above |
| `1h` | 730 days | the workhorse — two years in one request |
| `15m` / `5m` | 60 days | intraday |
| `1m` | 30 days, 7 per request | avoided — the stitching invites rate limits |

4H and other session timeframes are **resampled from `1h`** using
`future_roots.session_open` as the origin. Yahoo has no native 4H.

### Delay

Futures ~10 min, indexes ~15 min, US equities near-real-time. Fine for watching
markets, but **the active feed and its delay must be visible in the UI**.

### Rate limiting — a first-class constraint

Measured 2026-10-03: a **single** call to `v1/finance/search` returned 429 and
left the IP blocked for **every** subsequent `v8/chart` request, including 16
spaced 1.5s apart. Yahoo's limiting is far harsher than the plugin ecosystem
assumes.

Consequences, all mandatory:

- **Local search only.** Never call `v1/finance/search` on the typing path. At
  most a rare manual fallback for a missing symbol, behind an explicit action
  and exponential backoff.
- **The cache is the defense.** Downloading once and never again is both the
  speed principle and the rate-limit strategy — they are the same design.
- **Serialize and back off.** Concurrency capped at 1–2, hard backoff on 429.
- **Stale-while-error.** A 429 shows the cached chart with a staleness
  indicator, never an empty pane.

## UI and functionality

**Reserved — direction to come from the author.**

Settled so far: TradingView as the model for feel, native GNOME patterns for
form, speed over everything.

Constraints the data layer imposes regardless of design:

- Search is local and sub-millisecond, so search-as-you-type is always safe
- Charts paint from cache before any network call resolves
- The active adapter and its delay must be visible
- The forming (incomplete) bar must be visually distinct, or dropped
- Rate-limited or offline degrades to cached data with a staleness indicator,
  never a blank chart
